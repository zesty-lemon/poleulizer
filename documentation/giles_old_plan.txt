Over five weeks, I'll build a per-pole localization pipeline. I will take VAIL-annotated bus dashcam frames and, for every labeled pole, produce the set of (frame, camera view, bbox) observations across the three forward cameras — each tagged with a stable per-pole ID. Condition assessment was split off as a separate task at the 2026-05-13 meeting and is out of scope; this project ends at "given a pole, here are all the bboxes."

High Level Plan:

Week 1: Build the three-camera forward-projection pipeline (center, forward-left, forward-right). Given a pole's lat/lon, bus pose, and per-camera intrinsics + off-axis angle, output a predicted (u, v, scale) per camera. Validate visually on a sample of Batch-5 frames.
Week 2: Compute visibility windows. For each VAIL-labeled pole, walk backwards from the labeled frame through earlier frames and record every (frame, view) where the pole falls inside a camera's FOV cone. Validate against the closest-approach labels — every labeled pole should have a non-empty window.
Week 3: Fine-tune a detector on the weak labels from the visibility windows and stand up the FULL pipeline end-to-end with placeholder bbox matching, so Weeks 4–5 are quality work on a working system.
Week 4: Multi-pole frames. Implement Hungarian assignment between predicted pixel positions and detected bboxes for frames where multiple poles' visibility windows overlap. Evaluate against a small manual bbox set.
Week 5: Aggregate per-pole observations into the final parquet table keyed by (pole_id, frame_id, view), with bbox, range, and detection confidence. Ship + writeup.

The Localization Problem:

VAIL annotates each pole once, at closest approach — and at closest approach the pole is perpendicular to the bus heading, so it's outside the forward-camera FOV. The labeled frame is the one frame in the sequence where the labeled pole cannot be seen. To see it, we walk backwards. The visibility window is the contiguous range of earlier frames where the pole is still in a forward camera's cone.

Per-pole pipeline (for each VAIL-labeled pole P):
1. Compute P's visibility window by walking back from the labeled frame, checking bearing/range against each camera's FOV cone.
2. For each (frame, view) in the window, forward-project P into image space → predicted (u, v, top/bot).
3. Run the detector on the actual image → set of detected pole bboxes.
4. Match predicted position to detected bboxes. When multiple poles' windows overlap on the same frame, the matching is Hungarian assignment over {predictions × detections}.

Each VAIL-labeled pole becomes a row group in the output table. Bboxes the detector returns that don't match any expected pole are ignored in v1 — most of them are real visible poles VAIL didn't label, but localizing unlabeled poles is a stretch goal.

General Notes:

Image downloader and pole catalog builder are already built and smoke-tested. The catalog is keyed entirely by geohash-9 of the VAIL-provided coords — same physical pole across batches → same ~5m geohash cell → same pole_id. No state-utility database lookup, no match gate, no natural-id fallback. The earlier GMP/VEC/WEC fetcher and the 10m-gate match logic are parked in temp_junk/ and can be reintroduced as a post-process "promotion pass" later if the project ever needs canonical utility IDs.

Camera setup is three forward-facing dashcams: center, forward-left, forward-right. There are no true side cameras — left and right are still forward, just angled off-axis. This is exactly why walking backwards works: the bus drives toward each labeled pole, the pole is in one of the forward cones for several frames before closest approach, and the labeled frame itself sits at the far end of the window.

VAIL labels at most one pole per side per frame, so multi-pole frames don't come from a single annotation — they come from overlapping visibility windows of multiple distinct labeled poles. The Hungarian assignment in Week 4 is what handles that.



Full Timeline with Deliverables:

WEEK 1 — Forward-projection pipeline

Main track: For each of the three cameras, implement (lat, lon) + bus pose + camera intrinsics + per-camera off-axis angle + extrinsics → predicted (u, v, height_in_pixels). Validate visually on ~20 Batch-5 frames using known labeled poles: project the pole into the frame at, say, two frames before closest approach, and check the projection lands roughly where a pole is actually visible in the image.

Calibration is the biggest unknown coming in. Camera intrinsics and extrinsics aren't documented in the VAIL XML and have to come from Kamiku/VAIL — see open questions. Placeholder values (±15° FOV, median pole height ~12 m, mounting at bus roof height) until I get real numbers.

Deliverable: Working three-camera projection script + visual validation on ~20 frames + a written list of what I still need from VAIL to make the projection accurate.

WEEK 2 — Visibility windows

For every VAIL-labeled pole in Batch-5 (and any additional onboarded batches by then), walk backwards through the frame sequence from the labeled frame. At each step: compute bearing and range from bus to pole, check each camera's FOV cone, drop frames where range > r_max (placeholder 80 m). Record (frame, view, bearing, range, confidence) for every qualifying pair. Stop when the pole exits every cone or range exceeds the cutoff.

Validate against the existing closest-approach labels — every labeled pole should produce a non-empty window in at least one of the three views. Poles with empty windows indicate either a projection bug or a bad VAIL coord; both are worth investigating.

Deliverable: Per-pole table of (pole_id, frame, view, predicted_uv, range_m). Visual spot-check of windows for ~10 randomly chosen labeled poles. This is the weak-supervision layer the detector will train against in Week 3.

WEEK 3 — Detector + end-to-end prototype

Use Week 2's visibility-window predictions as weak training data — each prediction gives an approximate (frame, view, expected pixel region) that a detector should agree with. Fine-tune an off-the-shelf model (YOLO11 / RT-DETR / Grounding-DINO zero-shot baseline first to decide whether fine-tuning is even needed).

Critical: stand up the FULL pipeline end-to-end this week, even if bbox matching is just "nearest detection to the prediction." Producing some output parquet by end of Week 3 surfaces integration issues early and gives a working baseline. Weeks 4–5 are quality improvements, not first-time integration.

Deliverable: Trained or zero-shot detector + evaluation report (recall against the predicted-uv set, precision against a tiny manual bbox sample) + end-to-end pipeline emitting a placeholder version of the final parquet table.

WEEK 4 — Multi-pole assignment + evaluation

Replace nearest-detection matching with Hungarian assignment for frames where two or more visibility windows overlap. Cost: weighted combination of |u_pred − u_bbox| and |size_pred − size_bbox|. Single-prediction frames degenerate to the existing behaviour.

Build the evaluation set: manually label bboxes on ~30–50 frames spanning a few labeled poles' full visibility windows. This is the only manual annotation in the project — small, targeted, just enough to score the bbox-matching step. Use it to tune r_max, cost weights, and detection-confidence threshold.

Deliverable: Final matching logic + precision/recall numbers on the held-out manual bbox set + a short error analysis (where matching fails, why).

WEEK 5 — Aggregation + final output

Emit the deliverable parquet at data/localization/observations.parquet, keyed by (pole_id, frame_id, view), with columns: pole_lat/lon, bus_lat/lon/heading, bbox_x/y/w/h, range_m, detection_confidence, batch. The reverse view ("for pole X, give me every supporting frame") is a one-line GROUP BY.

Short methodology writeup: what the visibility-window math does, how the pipeline composes, what the manual evaluation set says about precision/recall, what's deferred (unlabeled poles, condition, catalog promotion).

Deliverable: Final observations.parquet + writeup + a few annotated example sequences showing one pole tracked across its visibility window.

ONGOING QUESTIONS

The camera questions are the top blocker — without intrinsics and extrinsics the forward-projection in Week 1 runs on placeholders and Weeks 2–5 inherit that error. Everything else is tunable.

Camera-side (VTrans / Kamiku / VAIL):
- Camera intrinsics for center, forward-left, forward-right: focal length, principal point, distortion coefficients.
- Camera extrinsics: rigid transform from each camera to the bus body frame (mounting height, pitch, yaw, off-axis angle for L/R).
- FOV cone width per view — estimate ±15° each as placeholder until measured.
- Are these standard across the bus fleet, or do I need per-bus calibration?

Project-side (decide myself, but worth noting):
- Pole height assumption for the forward-projection height check. GMP's POLEHEIGHT column gives per-pole values (35/40/45 ft typical) but VAIL labels don't carry pole height. Use a median (~12 m) until intrinsics are accurate enough that height matters.
- Detector: YOLO11/RT-DETR fine-tuned on weak labels vs Grounding-DINO zero-shot. Decide after one smoke test in Week 3.
- Range cutoff r_max. Placeholder 80 m. Tune empirically once a detector run is available.
- Evaluation. VAIL gives one labeled position per pole but no per-frame bbox ground truth. Plan: manually label bboxes on a ~30–50-frame held-out subset (Week 4) to score the bbox-matching step.
